# GPU 半透明渲染踩坑记：自动化竖线白边三层修复实录

> 2026-11。AR 折叠自动化竖线的白边/发白问题前后修了三轮才到位，中间两次
> 修出新的视觉 bug。把整条因果链和教训记录下来，避免下次再踩。

## 症状演变

| 阶段 | 表现 | 触发环境 |
| --- | --- | --- |
| 1 | 竖线边缘一圈白边 | 移动端（亮色主题最明显） |
| 2 | 重叠竖线略微加深（可接受但有） | 修复阶段 1 时引入 |
| 3 | 密集竖线区域被洗成一片白纹 | 修复阶段 1 的第二次尝试引入 |

## 渲染链架构（两端根本不同）

同一个 `fs_main_curve_premul` / `fs_main_curve` shader，两端走完全不同的
合成路径：

```
桌面（egui）:
  wgpu 离屏纹理（行背景由 egui 画在纹理外，纹理处透明）
    → GPU 混合（附着格式决定线性 or 原始空间）
    → egui register_native_texture（sRGB view 采样会解码）
    → egui 预乘合成到背景
  → 解码保持预乘不变量，合成正确

移动（Flutter）:
  wgpu surface / 外接纹理（行背景由 Flutter 画在 Texture 下层）
    → GPU 混合
    → Flutter 引擎按「预乘 alpha」在 sRGB 空间直接合成（无解码！）
  → 存储空间 ≠ 合成空间时，边缘像素过冲 → 白边
```

关键差异：桌面合成前有一次 sRGB 解码（采样时硬件做），能把"线性空间预乘"
的字节还原回线性再合成，预乘关系不变；移动端 Flutter 对外接纹理字节**原样**
当预乘 sRGB 用，谁存了别的空间的预乘值谁就出白边。

## 坑 1：sRGB 附着强制 GPU 线性混合（真正的根因）

- `Sink::surface` 当初刻意偏好 `is_srgb()` 格式（iOS 外接纹理视图也是
  `Bgra8UnormSrgb`）。
- sRGB 附着的语义：着色器输出被当作**线性值**，混合在**线性空间**进行，
  存储时硬件编码回 sRGB。
- 于是 GPU 混合存出的字节是"线性空间预乘"结果（`encode(linear_mix·cov)`），
  而 Flutter 按"sRGB 空间预乘"解读（`stored + bg·(1−cov)`）。`encode` 非线性，
  预乘关系在编码域被破坏：边缘像素 = 线色·A + 背景·(1−A) + 背景·(1−cov)，
  **背景被加了两次**，coverage 越低越亮，直接钳到白。
- CPU 把行背景预烘进实例色也无济于事——烘进去的那份背景在合成时又加了一次。

**修复**（`0e1160b`）：移动端 surface / iOS 外接纹理视图一律选**非 sRGB**
格式。整条「着色器输出 → GPU 混合 → 存储 → Flutter 合成」链路统一在 sRGB
空间，预乘不变量成立，白边在数学上不可能再出现过冲。AM 面板同源白边一并
修复（同一 `Sink::surface`）。

注意：桌面端**不要**跟着改。egui 的采样解码路径是自洽的，动了反而要重推
整套桌面合成。

## 坑 2：Max 混合的"并集"语义只对预乘值成立

折叠自动化预览用 `Max` 混合实现「整层 0.35 不透明度、重叠不加深」
（`dcd174dd`）。Max 取并集的前提是**边缘像素值 ≤ 核心像素值**（预乘值天然
满足：边缘 = 核心 × coverage）。

第二次修复时我让 shader 输出 `alpha=1` 的不透明像素（`mix(背景, 线色, α·cov)`
再 discard 掉 coverage=0 的填充），配合 Max 使用——前提被破坏：

- 不透明边缘带 ≈ 背景色，**不小于**核心色在饱和通道上的值
  （橙线核心 = (0.98, 0.88, **0.68**)，蓝通道 0.68 < 背景 0.94）。
- Max 逐通道取最大 → 相邻竖线的边缘带把核心的饱和通道吃掉
  → 橙色被洗成 (0.98, 0.94, **0.94**) ≈ 白色。
- 黑乐谱式密集竖线区域，边缘带互相覆盖核心 → 整片洗成白纹
  （用户截图："应该是实心的浅三角形，现在全是奇怪的白线"）。

教训：**换混合公式的语义时，必须检查"边缘 ≤ 核心"这条不变量还成不成立**。
Max 只对预乘（或单调随 coverage 递减的）值是并集。

## 坑 3：线性空间混色 vs sRGB 空间混色的观感差

第二次修复还把混色从 CPU 的 sRGB 空间搬进了 shader 的线性空间（"数学正确
的 AA"）。结果线体明显变淡：

- 亮色主题暗线：sRGB 混色核心 0.646 → 线性混色 0.78（背景 0.94），
  线几乎贴进背景里。
- 原因：gamma 不正确的混色会把半透明细线画得更粗更重——文字渲染故意用它
  就是为了细笔画不虚。

教训：**"色彩学正确"和"观感正确"不是一回事**。UI 细线/半透明线条的 alpha
混合在 sRGB 空间做往往才是想要的观感。最后回退后保留的 CPU sRGB 烘焙
（`91e419d`）观感就是用户熟悉的那个。

```

9ba00bc9  fix:  Max → 预乘 over——修了白边但引入重叠加深，且没找到根因
d5165ea   revert: 桌面恢复 Max（用户要"重叠不加深"）——保留 ✓
37464c99  feat:  OPAQUE_BAKED 不透明烘焙机制——引入坑 2 的白纹
66140411  fix:   混色改回 sRGB 空间——观感对了，但 Max 吃色仍在
91e419d   revert: 整套 OPAQUE_BAKED 机制删除 ✓
0e1160b   fix:   surface 改非 sRGB——真正的根因修复 ✓
```

最终保留的全部改动：

1. `yinhe-flutter/render.rs`：`Sink::surface` 偏好非 sRGB 格式；iOS 外接
   纹理视图 `Bgra8Unorm`。仅此而已。
2. 桌面 `curve_overlay_pipeline` 保持 Max 混合（透明目标上并集语义正确）。
3. 移动端保持原有 CPU 烘焙（sRGB 空间混背景、输出 alpha=1）+ 直通 alpha
   混合路径——在非 sRGB 附着上，这条链路自身就是正确的。

## 经验法则

1. **半透明内容经过外接纹理/UI 框架二次合成时**，先确认合成方的 alpha
   语义（Flutter 外接纹理 = sRGB 空间预乘）和附着格式，让「混合空间 =
   存储空间 = 合成空间」，任何一步错位都会在 AA 边缘现形。
2. **sRGB 附着会偷换混合空间**。想在 sRGB 空间混合（UI 观感），附着就不能
   是 sRGB；想线性混合，就得保证下游合成也在线性空间（或有人帮你解码）。
3. **换 blend 公式前先写下不变量**（如"边缘 ≤ 核心"），并确认新输入满足它。
4. **GPU 像素回归测试**值得写，但测不到合成阶段——白边发生在我们的渲染器
   之外，最终只能靠真机/模拟器目检。渲染端能测的是"线上所有像素 alpha=255"
   这类不变式。
5. 连续几轮修不好时，回头怀疑**架构假设**（这里 = "surface 格式无所谓"），
   而不是继续在 shader 里叠补丁。
