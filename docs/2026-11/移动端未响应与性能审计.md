# 移动端「未响应」与性能审计

- 日期：2026-11-21
- 范围：Flutter 移动端（Android 为主，iOS/OHOS 共用 Rust 路径）、`crates/yinhe-flutter`、`crates/yinhe-mobile-core`，以及它们依赖的 `yinhe-wgpu` / `yinhe-core` / `yinhe-editor-core` 热路径。
- 方法：代码路径静态分析、复杂度与内存量级推算、历史提交比对。**没有做真机 profiler 采样**，因此文中的毫秒数都是量级估算，只用于排序，不作为验收指标。
- 证据等级：
  - A：代码路径可直接确认（例如同线程二次加锁）。
  - B：复杂度/内存推算，结论方向确定，具体数值待实测。
  - C：需要真机日志或 ANR trace 才能确认。

---

## 0. 结论

移动端「未响应」不是单一问题，而是三层问题叠加：

1. **两个必现/高概率死锁（与音符数量无关）**
   - 钢琴卷帘的音符预览在持有 scene 锁时调用音频模块，音频模块又去拿 scene 锁，同线程自锁。
   - 播放中执行撤销/重做/粘贴等后台文档任务时，后台线程「audio → scene」与 UI 线程「scene → audio」形成 ABBA。

2. **与音符数线性放大的每帧工作**
   - AR 视图的音符层缓存键包含 `scroll_x/scroll_y`，播放跟随或滚动时每一帧都全量重建可见音符。
   - 大 MIDI 默认以「整曲适配」打开 AR，可见 tick 范围约为整曲的 15%-30%（手机屏宽 / 2560）；1 亿音符时每帧扫描千万级音符。
   - UI 线程每帧同步等待渲染线程 present 完成，最长 500ms，上述每帧工作直接变成 UI 冻结。

3. **与选中数/事件数线性放大的单次操作**
   - 拖动松手、橡皮擦、缩放、Riff 在 UI 线程同步处理整个选区。
   - 选区 ghost 物化按每个选中音符 12B 存储，1 亿选中约 1.2GB，且不取消旧任务。
   - AM 面板打开时，每次编辑都全量序列化该轨所有自动化 lane；AM 锚点拖动每帧 O(锚点+事件)。

**最可能直接对应「大量用户报告未响应」的三条**：

- 只要用户在 PR 里用铅笔落音、拖动音符或改长度，就会踩到第 1 条自锁（A 级）。
- 只要用户打开大 MIDI 后在 AR 里播放或滚动，就会踩到第 2 条每帧全量重建（A+B 级）。
- 只要用户「边播放边编辑/撤销」，就有概率踩到 ABBA（A 级）。

这三条都能让界面长时间不响应，且用户不需要知道具体操作名，只会描述为「音符多了就卡死」。建议先按第 11 节的批次 1 修，改动都很小。

## 2. P0-1：PR 音符预览的 SCENE 自锁（必现）

### 2.1 锁模型

- `scene()` 是 `OnceLock<Mutex<RenderScene>>`（`scene.rs:582-586`），`std::sync::Mutex` 不可重入。
- 移动端所有编辑入口都在 Dart UI isolate 上同步执行，即都在同一线程。

### 2.2 调用链

以「铅笔在 PR 空白处落音」为例：

```
Dart: yinhe_edit_begin
  → edit::begin (lifecycle.rs:67)
  → begin_with_tool (lifecycle.rs:76)
  → scene().lock() 持锁 (lifecycle.rs:88)
  → begin_pr (lifecycle.rs:103)
  → Tool::Pencil 分支 preview_note (lifecycle.rs:1039)
  → preview.rs:178 audio::preview_notes
  → audio.rs:810 ensure_audio
  → audio.rs:813 recover_stream_error
  → audio.rs:656 current_model()
  → audio.rs:1099-1101 scene().lock()   ← 同一线程第二次加锁
```

同类入口：

| 操作 | 持锁点 | 预览调用 |
|---|---|---|
| 拖音符起手 | `lifecycle.rs:517` | `lifecycle.rs:553` |
| 改长度起手 | `lifecycle.rs:359` | `lifecycle.rs:388` |
| 铅笔压已有音符 | `lifecycle.rs:88` | `lifecycle.rs:1025` |
| 铅笔空白落音 | `lifecycle.rs:88` | `lifecycle.rs:1039` |
| 选框内长按起手 | `lifecycle.rs:88` | `lifecycle.rs:1000` → `preview.rs:282` |
| 拖动中改音高 | `lifecycle.rs:140` | `preview.rs:746/1010` |
| 每帧边缘滚动 | `lifecycle.rs:178` | `lifecycle.rs:255` → `preview.rs:746` |
| 长按转移动态 | `lifecycle.rs:821` | `lifecycle.rs:828` |

`preview_note` / `preview_group` 的参数是 `&RenderScene`（`preview.rs:164/239`），这两个函数本身就假定调用方已经持有 scene 锁；所以锁内调用音频不是偶然，而是现有 API 形态导致的。

### 2.3 为什么是「未响应」而不是卡一下

`recover_stream_error` 第一行无条件取模型，不先判断 `stream_error()`：

```rust
pub fn recover_stream_error() -> bool {
    let model = current_model();          // ← 这里就二次加锁
    let Some(mut guard) = lock_audio() ...
    if !st.handle.handle.stream_error() { return false; }
    ...
}
```

`std::sync::Mutex` 同线程二次 `lock()` 会永久阻塞。UI 线程被卡住后，Dart 无法处理触摸/渲染，用户只会看到「未响应」。

触发前提只有两个：

- 音频引擎存在（首次预览会通过 `ensure_audio` 创建，所以几乎是必然）；
- 音符力度大于 `ignore_velocity`（默认 1，正常音符都满足）。

即使力度全被过滤，`preview_notes` 会走 `stop_preview`，仍然在持 scene 锁时拿 audio 锁，构成下面 P0-2 的 ABBA 风险，只是不再自锁。

补充：在走到自锁之前，`begin_note_move` / `begin_note_resize` 还会先执行 `hit_note` 的全 key 桶扫描（`edit/hit.rs:17`）。文件越大，这段扫描越久，用户会感觉「音符越多越容易卡」，但真正的永久阻塞来自后面的自锁。

### 2.4 修复方向

**最小修复（一行）**：删掉 `preview_notes` 里的 `recover_stream_error()`。

理由：

- Dart ticker 已经每 60 帧调用一次 `yinhe_audio_recover`（`studio_shell.dart:733-735`）；
- `play()` 在 `audio.rs:925-928` 已经先 `ensure_audio` 再 `recover_stream_error`；
- 预览不需要承担「修复死流」的职责，而且它本身在锁内，做这件事必然危险。

**彻底修复**：把预览从「持锁调用音频」改成「锁内收集参数，锁外提交」。例如让 `begin_pr` / `refresh_preview` 返回一个 `Option<PreviewBatch>`，在 `drop(s)` 后统一调用 `audio::preview_notes`。`edit::end` / `tap_note` 已经是这种写法（`lifecycle.rs:924-938`）。

**回归测试**：`crates/yinhe-mobile-core/src/edit/tests.rs` 目前只有 86 行，完全没覆盖预览/手势路径。建议增加一个 `debug_assert!(scene().try_lock().is_ok())` 级别的守卫，或在 `current_model()` 里用 `try_lock` 并在调试构建下 panic，保证同类错误在测试中立刻暴露。

## 3. P0-2：播放中编辑的 ABBA 死锁（高概率）

### 3.1 两个方向的调用链

UI 线程（每帧 `view_snapshot`）：

```
yinhe_view_snapshot
  → scene/view.rs:549  scene().lock()            [持 SCENE]
  → scene/view.rs:559  audio::playback_tick_for
  → audio.rs:1074      lock_audio()               [等 AUDIO]
```

后台文档任务线程（撤销/重做/粘贴/批量编辑完成时）：

```
doc_job.rs:130 audio::reload_notes(model)
  → audio.rs:858  lock_audio()                    [持 AUDIO]
  → audio.rs:861  snapshot_playback
  → audio.rs:893  flow_sync_cursor
  → audio.rs:1112 current_model()
  → audio.rs:1100 scene().lock()                   [等 SCENE]
```

播放中 `flow_sync_cursor` 才会进入 `current_model()`（`audio.rs:1111`），因此触发条件明确：**播放中 + 后台文档任务完成 + UI 正好在 view_snapshot**。

UI 每帧都会调用 `view_snapshot`（`shell_core.dart:6-11`），后台任务持 AUDIO 的窗口虽短，但 `reload_notes` 在 `rebuild_for_model` 需要重建时会在锁内 `spawn_audio`（数百 ms），窗口会被显著放大。两者一旦相撞就是永久死锁。

### 3.2 修复方向

不要让 `flow_sync_cursor` 在持有 AUDIO 时再拿 SCENE：

- `snapshot_playback` / `reload_notes` / `update_notes` 的调用方本来就有 `Arc<YinModel>`；
- 把 `flow_sync_cursor(st, model: &YinModel)` 改成用传入模型计算 `seconds_to_tick`；
- `play()` 也按同样方式先取模型快照再进 AUDIO。

这样 A→S 的边消失，ABBA 不存在。

另外建议统一一条规则并写进注释：**任何 `lock_audio()` 内的代码不得再调用 `scene()`**。可以用 `debug_assert` 包一层 `with_audio(|st| ...)` 辅助函数，在调试构建下用 `scene().try_lock()` 检查。

## 4. P0-3：AR 音符层每帧全量重建（大 MIDI 的主要卡顿源）

### 4.1 缓存键包含了不该包含的滚动

`ArrangementView::render_hash()`（`arrangement_view.rs:195-203`）：

```rust
hash_f32s(&[
    self.base.pixels_per_tick,
    self.base.scroll_x,      // ← 每帧滚动/播放跟随都会变
    self.base.scroll_y,      // ← 纵向滚动每帧都变
    self.base.left_panel_width,
    self.lane_height(),
])
```

而 `NoteInstance` 只存 `(start_tick, end_tick, key, track, velocity)`（`arrangement/instances.rs:49-53`）。shader 里：

- x/w 由 `ppu + scroll_x` 在 GPU 计算（`shader.wgsl:308`）；
- y/h 由 `lane_height + scroll_y + track_offsets` 在 GPU 计算（`shader.wgsl:510-519`）。

也就是说，**滚动只应该改 uniform，不应该让实例缓存失效**。代码注释本身也写了 `scroll_y changes do NOT invalidate the cache`（`arrangement/instances.rs:84-88`），但 key 实际包含了它，注释与实现矛盾。

### 4.2 触发频率

- 横向平移：每帧 key 变；
- 纵向平移：每帧 key 变（纯浪费，实例不含 y）；
- 播放跟随：`apply_follow` 每帧改 `scroll_x`（`scene/view.rs:677-745`），默认 `follow_playhead = true`；
- 任意编辑：`refresh_snapshot` bump revision（`scene.rs:601-604`），key 变；
- 增删音符：`note_count` 参与 key（`upload.rs:268`），key 变。

### 4.3 单次重建做什么

`upload_arrangement`（`render/upload.rs:263-299`）→ `build_notes`（`arrangement/instances.rs:94-166`）：

1. 对 128 个 key 并行；
2. 每个 key 调 `key_notes_in_range(key, tick_start, tick_end)`，**扫描可见 tick 范围内该 key 的所有轨道音符**；
3. 扫描后才按 `trk_first/trk_last`、`track_visible` 过滤；
4. 每个 key 分配 `vec![Vec::new(); num_tracks]`（`instances.rs:119`），799 轨时每帧新建 128×799 ≈ 10 万个 Vec；
5. 合并前每个可见音符还要先 push 到 `track_buckets[ti]`（`Vec<(u32,u32,u8)>`，12B）。1 亿工程默认 AR 下，单次重建的临时缓冲可达数百 MB，且每帧重新分配/释放。即使最终亚像素合并后实例很少，扫描和临时内存也已经付过；
6. 做亚像素合并后写入 `notes_buf`；
7. `out.extend_from_slice(notes_buf)` 再拷进层 scratch（`upload.rs:298-299`）；
8. `queue.write_buffer` 整层重传。

所以「只改滚动」时会付出：全量扫描 + 实例构造 + 合并 + 多次内存拷贝 + GPU 上传。

### 4.4 默认缩放让问题最大化

`apply_document`（`scene/file.rs:695-700`）：

```rust
pixels_per_tick: (1280.0 * 2.0 / content_ticks as f32).clamp(...)
```

手机打开工程默认进入 AR（`scene/file.rs:725`）。初始 `ppu = 2560 / content_ticks`，所以横向可视比例约为「逻辑屏宽 / 2560」：手机常见 15%-30%，平板更高。1 亿音符、300 万 tick 的工程，单次重建要扫描约 1500-3000 万音符（实际受 key 范围和亚像素合并影响，但量级不变）。

`NoteSource::key_notes_in_range` 的左界还会被 `max_note_len` 再放宽（`yinhe-types/src/source.rs:55-58`），只要工程里有一个超长音符，扫描起点会退到更早，甚至 tick 0。

### 4.5 修复方向

按 PR 的 `NoteLayerCache::plan_window`（`note_cache.rs:40-58`）的做法给 AR 也建窗口：

1. 可见 tick 范围 `[lo, hi]`；
2. 窗口 = `[lo - span/2, hi + span/2]`，按 `span` 对齐；
3. 缓存键使用 **窗口的 tick_start/tick_end + ppu + 可见轨道集合 + revision**，不再使用 `scroll_x/scroll_y`；
4. `build_notes` 接受显式窗口参数，而不是从 view 现算；
5. 窗口不变时只更新 uniform。

这样：

- 播放跟随、滚动在窗口内零重建；
- 纵向滚动彻底不重建（实例本来就不含 y）；
- 只有跨窗口、缩放跨档、显隐/编辑时才重建。

另外：

- 去掉每 key 的 `vec![Vec::new(); num_tracks]`：可以按 `(key, track)` 直接用 `HashMap`/排序后分段，或复用 `Target` 里的 scratch；
- 先按可见轨道过滤再构造，能减少无效 `push`，但扫描量只有按轨道分桶索引才能根治；
- `build_ghost_notes` 目前每帧 `preview.ghost.as_ref().clone()`（`upload.rs:307`）再原地排序，应该把 clone 移到「确定要重建」之后，或在已有顺序上直接构建。

## 5. P0-4：UI 每帧同步等待 present + 常驻 ticker

> 2026-11-21 更新：`yinhe_render_frame` 已改为非阻塞请求，500ms 已删除。下面保留原始分析，ticker 空闲停帧仍未做。

### 5.1 机制

- `yinhe_render_frame` 用 `sync_channel(1)` 发 `Cmd::RenderNow`，然后 `recv_timeout(500ms)`（`dart_ffi/playback.rs:135-147`）。
- 渲染线程收到后执行 `render_frame`（含 CPU 构建、`queue.submit`、`sink.present`），完成后才回信（`lib.rs:401-411`）。
- Flutter ticker 每帧同步调用 `rust.renderFrame()`（`studio_shell.dart:648-660`），并在结尾无条件 `scheduleFrame()`（`studio_shell.dart:756`），空闲也不停。

结论：**渲染线程的任何慢帧都会直接变成 Flutter UI 线程的阻塞**。P0-3 的每帧重建、AR 自动化层重建、AM 渲染、GPU present 等待，全部会传递到 UI。

### 5.2 放大效应

- 单帧渲染 300ms → UI 每帧卡 300ms；
- 连续慢帧 → 输入队列持续积压，用户看到「未响应」；
- 500ms 超时只是兜底，而且超时后 Flutter 继续画上一帧，下一帧仍然要等，问题不会自愈；
- 空闲时也以 60/120Hz 跑完整个 FFI + 渲染链路，手机发热后降频，进一步放大。

### 5.3 修复方向

分两步：

1. **先消除慢帧**（P0-3、P1-2、P1-7）。在渲染线程仍然会做重活时，改非阻塞只会让画面落后，不能解决卡顿。
2. **给等待加安全阀**：把 `recv_timeout(500ms)` 降到一帧级别（例如 8-16ms），或改成 `try_recv`，让 UI 最多落后一帧而不是被单帧拖 500ms。需要同时确认 overlay 与纹理的对应关系：目前依赖「同帧产出」，如果改成非阻塞，应该给 overlay 数据带一个 frame revision，Flutter 读取与纹理同 revision 的快照。

**ticker 按需启动**：维护一个 `_needsFrame` 状态：

- 播放中；
- 惯性/边缘滚动/拖拽；
- 长按圆环；
- 主题过渡、AM 高度动画；
- 其他一次性动画。

只有这些状态为真时才 `scheduleFrame()`，空闲时停帧。这个改动不解决 ANR 根因，但能显著降低发热和后台 CPU 占用。

## 6. P0-5 / P0-6：大选区提交与物化

### 6.1 提交都在 UI 线程，且持 DRAG + SCENE 两把锁

`edit::end`（`lifecycle.rs:841-940`）在 UI 线程同步执行：

| 手势 | 提交函数 | 主要工作 | 复杂度 |
|---|---|---|---|
| 移动 | `commit_move`（`commit.rs:318-376`） | `move_selected_notes` / `move_selected_arrange` | fast ≈4-6 遍 N；slow ≈6-8 遍 + 全桶重拷 |
| 缩放 | `commit_selection_scale`（`commit.rs:233-255`） | `rescale_selection_span` | 无 fast path，O(N log N + 触达桶总长)，undo 2N |
| 改 gate | `commit_selection_gate`（`commit.rs:282-316`） | `resize_selected_notes_min_gate` | fast O(N)；slow O(N log N) |
| Riff | `commit_riff`（`commit.rs:390-482`） | `repeat_selected_keys_extent` | O(N×K)，undo 20B×N×K |
| 橡皮 | `commit_erase`（`commit.rs:628-710`） | **UI 线程 `materialize_pending`** + `delete_selected` | O(N log P)，undo 20B/音符 |

`move_selected_notes` 的快路径（`move_resize.rs:30-80`）虽然是就地修改，但仍要：

- 全选区 clamp 预扫；
- `NoteBucket::update_matching` 逐块 `Arc::make_mut`（渲染线程持有旧模型时，每块 65536 音符 = 1MB 深拷贝）；
- `rebuild_dirty` 对每个脏桶再扫 2 遍；
- `sort` 有序性检查 1 遍。

慢路径（换 key / 重叠）要 `remove + insert_batch + rebuild_dirty`，峰值同时存在 5-6 份 N 量级数据（`move_resize.rs:82-174`）。

### 6.2 亿级量级

按顺序扫描 2-5ns/音符、BTreeMap 命中 50-100ns/次估算：

| 操作 | 100 万选中 | 1 亿选中 |
|---|---|---|
| move 快路径 | 20-60ms / 12MB 位图 | 2-6s / 1.6GB COW |
| move 慢路径 | 0.3-1s / ~100MB | 30-120s / 5-6GB |
| scale | 0.2-0.5s / 40MB undo | 30-90s / 4GB undo |
| erase | 0.2-0.5s 冻结 | 20-40s 冻结 / 2GB undo |
| Riff（K=8） | 1-3s / 300MB | 60s+ / 16GB（必 OOM） |

### 6.3 选区物化的内存放大

`selection_materializer`：

- `schedule` 对新框选/全选起后台线程做 `Selection::materialize_pending`（`selection_materializer.rs:62-93`）；
- `schedule_drag` 在第一次按下选区时再起线程 `collect`（`:100-142`）；
- `collect` 输出 `DragData.by_key`：每个选中音符 12B（`DragNote = (u16,u32,u32,u8)`）；
- `HiddenNotes` 1 bit/音符。

1 亿选中：

- `by_key` 约 1.2GB（Vec 增长峰值可能 1.8GB）；
- `HiddenNotes` 约 12.5MB；
- 旧 `CachedDrag` 可能同时存在；
- `DragState.drag` 在提交后**不会清空**（`end`/`cancel` 都没有 `d.drag = None`），会一直保留到下一次 `begin_with_tool` 的 `*d = DragState{...}`（`lifecycle.rs:80`）才在 UI 线程释放。

`schedule_drag` 没有 single-flight：连续按下/移动会并发出多份全量 `collect`，每份 1.2GB。手机上非常容易 OOM 或被系统杀死。

`materialize_pending`（`selection.rs:193-220`）对每个命中音符调用 `NoteBitset::insert`：

- `BTreeMap` 页查找 + 可能 CoW 8KB 页；
- 每次 insert 都执行一次全局 `AtomicU64` 自增；
- 现成的 `NoteBitsetBuilder`（`note_bitset.rs:76-108`）一次分配 + build 时取一次版本号，快 5-10 倍，但这里没用。

`select_all_pr`（`document/selection.rs:45-88`）按「每轨一个 rect」生成 T 个矩形，而不是一个全局矩形 + 排除条件：

- `materialize_pending` 对每个 rect 扫描全部 key 桶 → O(T×N)；
- 物化完成前 `accepts_note` 对每个音符遍历 T 个 rect → O(T)/音符；
- `Selection` 顶部注释还写着「1 亿全选 = 1 个 rect」，与实现不符，需要同步。

### 6.4 修复方向

1. **物化统一用 `NoteBitsetBuilder`**；对 `select_all_pr` 的 T 个 rect 先按 key 合并 tick 区间（已有 `merged_tick_ranges_by_key` 思路），避免每个 rect 扫全部 key。
2. **拖动 ghost 不再存 12B/音符**：成员位图已经能精确判定「哪些音符被选中」，拖动时每帧只扫描可见区音符（O(视口)）并查位图，即可生成可见 ghost。这样 1 亿选中只需要 12.5MB 位图，不需要 1.2GB `by_key`。
3. `schedule_drag` 加 single-flight（in-flight 标记或 generation 抢占），并在 `end` / `cancel` 清 `d.drag`，同时把大对象释放移到锁外。
4. 大提交统一走 `doc_job`（已有进度框和后台线程），不要按「选中数阈值」分支；用一致的行为避免两套路径。
5. `erase` 的同步 `materialize_pending` 必须去掉：要么复用已有的成员位图，要么把过滤删除改成后台任务。
6. undo 增加字节预算，而不是只限 100 条（`history.rs:24`）。

## 7. P0-7：AM 锚点移动/直线的 O(M²)

### 7.1 批量移动

`move_automation_events_batch`（`automation_edit.rs:525-607`）：

```rust
for (old_tick, _, _) in moves {
    if let Some(idx) = events.iter().position(|e| e.tick == *old_tick) { ... events.remove(idx); }
}
...
for (new_tick, ...) in merged {
    if let Some(idx) = events.iter().position(|e| e.tick == new_tick) { ... events.remove(idx); }
    let insert_idx = events.partition_point(...);
    events.insert(insert_idx, evt);
}
```

每个 move 都是一次线性查找 + `Vec::remove/insert` 的 memmove。M 个选中锚点、lane 有 E 个事件时是 O(M×(E+M))。M=1e4、E=1e5 就是 10^9 级操作，UI 线程冻结数十秒。

`build_lane_multi_move`（`automation/ghost.rs:79-119`）在渲染线程里也是同样的 `position + remove`，而且每帧先 `lane.events.clone()`。AM 拖动时每帧都会做一次。

### 7.2 AM 直线绘制

`automation_line`（`scene/edit.rs:1082-1171`）按量化间隔生成点（`line_ticks`），然后 `upsert_automation_events_batch`（`automation_edit.rs:112-167`）对每个新点执行 `lane.events.iter().find`，再 `lane.upsert`。点数 × lane 事件数，跨全曲画线时非常危险。

### 7.3 修复方向

- 批量移动：先 `sort by old_tick`，用一次双指针扫描移除；再用 `BTreeMap`/归并重建 lane，而不是逐个 `remove/insert`。
- ghost 层不要 clone 整条 lane；只构建可见窗口内的锚点，或者让渲染线程直接读 `selected_ticks` + lane 的不可变快照。
- 直线：用 `partition_point` 定位插入区间，然后一次性 merge，而不是逐点 find/upsert。

## 8. P1：与音符数/事件数放大的第二梯队

### 8.1 力度摘要每次编辑全曲扫 8 遍

`poll_velocity_summary`（`renderer.rs:553-593`）在每次 revision 变化时启动后台线程，`VelocitySummary::build`（`velocity_summary.rs:45-98`）对 8 个档位各完整遍历 128 个 key 的全部音符：

- 扫描量 = 8×全曲音符数；
- 1 亿音符约 8 亿次迭代，读取模型 8×1.6GB；
- AR 视图也预热（`render.rs:500-506` 不判断视图），但 AR 根本不显示力度条；
- 连续编辑时一个任务完成、下一个 revision 又触发，持续抢满 CPU；
- `clear_velocity_summary` 不 join 旧线程，换文档时可能两份全量扫描并存。

建议：

- 只在 PR 视图预热；
- 只在 AM 面板可能显示力度时构建（或首次展开时构建，接受一次延迟）；
- 给任务加取消/代次检查，旧模型任务在扫描过程中定期检查 `generation` 并退出；
- 高密度工程先构建低档位摘要，按需再算细档（注意：不要引入按阈值的不同行为，可以作为「按需计算」而不是「不同语义」）。

### 8.2 `automation_json` 每次编辑全量序列化所有 lane

`automation_json`（`scene/automation.rs:9-64`）遍历该轨**所有** PB/CC/RPN lane 的所有事件，逐点 `format!` 成 JSON。AM UI 一次只显示一条 lane，但数据是全量的。

调用点：

- `_loadAutomation`（`shell_transport.dart:6-32`）在 AM 展开时调用；
- `_refreshDocumentMeta`（`shell_core.dart:186-218`）在每次编辑提交后、AM 展开时调用；
- ticker 每 4 帧检查 `document_generation`，编辑后触发。

后果：一条 100 万事件的 CC lane，每次拖音符/改力度/删事件都会生成数 MB 字符串并 `jsonDecode`，在 UI 线程上几十到几百 ms；多 lane 叠加更严重。

建议：

- 拆成「lane 元数据列表」和「单条 lane 的点」两个接口，只传当前显示 lane；
- 点数据按可见 tick 窗口裁剪，滚动时增量/重取；
- `automation_json` 的字符串拼接改用 `serde_json` 序列化或直接输出二进制；
- 编辑提交后的自动刷新改为「AM 面板可见且空闲时刷新」，不要和每次提交强绑定。

### 8.3 事件列表分页的 `take = skip + limit`

`events_json`（`scene/events.rs:430-561`）：

- 对 128 个 key 各取 `take = limit + skip + 1`；
- 对每条 lane 也取 `take`；
- 全部塞进 `rows` 后 `sort_by`；
- 最后 `rows[skip..end]` 只取一页。

黑乐谱同一个 tick 上百万音符很常见。用户跳到同 tick 巨簇的第 k 页时，`skip` 线性增长，`take` 也随之增长，128 个 key 同时放大，单次可能构造上千万行。

另外每行 `event_row_json` 调 `bar_beat_text_for_model`，后者每次 `build_time_sig_segments + compute_bar_offsets`（`time_format.rs:82-112`），O(拍号事件)/行。

建议：

- 分页游标改成 `(tick, 稳定 tie-breaker id)`，不要用 skip；
- 用 k 路归并而不是「每个 key 先取 take 再全排序」；
- 事件行的 `bar.beat.tick` 预计算（按 tick 分段缓存一次），不要每行重建分段；
- 事件列表打开/翻页放到后台任务，Dart 侧分页加载。

### 8.4 命中测试线性扫描整个 key 桶

`hit_note`（`edit/hit.rs:4-68`）直接 `for note in key_notes(key).iter()`，没有按 tick 二分。`note_velocity` / `note_at_bounds` 也是全桶 `iter().find`。

黑乐谱单 key 常达 10^6-10^7 音符，单次命中测试 5-50ms，触屏拖动时每次按下都要付。

建议：

- 用 `key_notes_in_range(key, tick-pad, tick+pad)`；
- 如果 `max_note_len` 很大，给 `NoteBucket` 增加每块最大 end 值，向前扫描时用块级 `max_end < tick_start` 剪枝；
- `NoteBitset`/选区判定同理。

### 8.5 PR 的 LOD 只减少输出，不减少输入

`NoteLayerCache::update`（`note_cache.rs:182-202`）：

```rust
let mut instances = build_key_notes_in_range(...); // 先构造全部原始实例并排序
if let Some(block) = summary_block {
    instances = build_key_summary(key, &instances, block); // 再压缩
}
```

`build_key_instances`（`pianoroll/instances.rs:76-96`）逐音符 push 16B 实例并 `sort_unstable`，`accepts_note` 还可能是 BTreeMap 查找。缩放到摘要档时仍然先做全量输入扫描、实例构造、排序，再聚合。

> 2026-11-21 已改为 `build_key_summary_in_range`：直接遍历 `NoteSource` 聚合，不再构造/排序原始实例。

建议：

- 摘要构建直接在原始 note 迭代上做块聚合，跳过 `NoteInstance` 中间层；
- 或者保留中间层但只在原始层需要时构造（LOD 档下不构造）。

### 8.6 标尺/网格/事件行/标尺标签每帧重建

- `_maybeRefreshRuler`（`studio_shell.dart:422-475`）在 `ppu/scroll_x/left_panel_w` 变化时调用 `ruler_labels_json` + `time_grid_json`。播放跟随时 `scroll_x` 每帧变 → 每帧生成 JSON + `jsonDecode`。
- `ruler_labels_json` / `time_grid_json`（`scene/view.rs:357-543`）每次都 `build_time_sig_segments` + 从第 0 段遍历到可视区，O(总拍号事件 + 可见标签)。
- `MarkerLayer`（`ruler_markers.dart:120-173`）每次 snap 变化都 `[...markers]..sort(...)`；空文本 marker 每个都调 `barBeatText`（FFI + 重建拍号分段）。
- `_EventRowsPainter._paintEvents`（`event_rows_bar.dart:411-440`）从第 0 个事件线性扫到可视区，`x < clip.left` 只是 `continue`。

建议：

- 标尺/网格的分段结果按拍号 revision 缓存（不是按时间缓存），只在拍号变化时重建；
- 可见标签用二分定位起点，而不是从 0 遍历；
- marker 排序结果按 markers revision 缓存，滚动只重算 x；
- 事件行 painter 用二分定位第一个可见事件。

### 8.7 轨道重排/删除/改名整表重写

- `move_track`（`track_ops.rs:630-690`）调 `apply_track_remap`（`model.rs:1276-1317`），即使只是交换两条轨，也会遍历 256 个桶、`Arc::make_mut` 每个桶、`retain_mut` 全部音符 → 全量 1.6GB 重写。
- `delete_track`（`track_ops.rs:556-627`）同样 `apply_track_remap_collect` + `rebuild_stats_only`，并收集所有被删音符进 undo。
- `set_track_info` / `set_track_name` 的 `Arc::make_mut(track)` 会深拷贝该轨的 `automation_lanes` / `audio_clips` / `clips`（这些是内联 Vec），CC 多时几十 MB。

建议：

- 纯重排时，音符的 track 号不必立即重写：可以在渲染/查询时用「track remap 表」映射，或者改成稳定 track id，显示顺序与 id 解耦；
- 删除轨道时只处理该轨音符，而不是全表 remap；
- 改名等元数据操作不要碰 `TrackData` 的大字段，拆出独立的元数据 Arc 或使用 `im` 风格的持久结构。

### 8.8 `max_note_len` 只增不减导致查询退化

`YinModel::max_note_len`（`model.rs:899-902`）是全局最长音符，只增不减。`key_notes_in_range` 左界 = `tick_start - max_note_len`（`source.rs:55-58`）。

只要工程里有一个整曲长音符（pad、环境音、导入的异常事件），所有 AR/PR/力度/选区范围查询都会从很早的 tick 开始扫。删除该音符也不会恢复，直到重新加载工程。

建议：

- 每个 key 维护自己的 `max_note_len`，而不是全局；
- 或者用块级 `max_end` 索引，让查询能按块剪枝；

### 8.9 音乐库/设置页的同步 IO

- 音乐库改为后台任务 + 缓存（按路径/修改时间失效）；

### 8.10 AM 面板自身

- `_handlePanUpdate`（`automation_panel.dart:1276-1290`）每个 pointer move 遍历 `lane.points` 全部点，再 `setState` 整个面板；

## 9. P2：常驻开销、内存与结构性重复

### 9.1 空闲每帧固定税

ticker 每帧固定调用（`studio_shell.dart:648-760`）：

- `dragTick`、`renderFrame`、`autoPauseAtEnd`、`playheadX`、`viewSnapshot`、`overlayRevision/overlayJson`、`selectionState`、`barBeatText`、`isPlaying`；
- 每 4 帧：`documentGeneration`、`docState`、`archiveStatus`、`sfLoadingJson` + `jsonDecode`、`autosaveTick`；
- 每 60 帧：`recoverAudio`。

即使空闲，每秒也有 60-70 次 FFI、60 次字符串分配、15 次 JSON 解码。单次都不贵，但会持续占用 CPU、阻止降频，并让任何一次慢帧更容易被用户感知。ticker 按需启动是收益/改动比很高的一项。

### 9.2 启动时在 Android 主线程建音频

`MainActivity.configureFlutterEngine`（`MainActivity.kt:188-194`）调 `nativeInitContext`，Rust 侧在 `android.rs:187` 调 `scene::ensure_starter_document()`，其中 `apply_document` 末尾 `on_model_loaded`（`scene/file.rs:734`）会同步 `spawn_audio`。

`spawn_cpal_audio` 包含设备枚举、引擎创建、流创建，桌面端专门放到后台线程并注释「UI 线程同步执行会冻结几百 ms」（`yinhe-egui/src/app/audio.rs:144-146`）。移动端没有搬这个优化。

影响：冷启动卡顿，首次播放/预览时也可能在锁内建流。建议把 `ensure_audio` 改成后台启动 + 轮询/回调，和桌面对齐。

### 9.3 内存放大

- `Note` 16B/音符，1 亿 = 1.6GB；
- 渲染线程持有 `Arc<YinModel>` 跨整帧（`render.rs:439-467`），编辑侧 `Arc::make_mut` 会 CoW 深拷贝被触达的块；
- undo 只限 100 条，不限字节；大选区一次 move/scale/erase 的 undo 可达 GB；
- `DragData.by_key` 1.2GB/亿选中；
- 加载新工程时新旧模型可能同时存在。

手机可用内存通常 2-4GB，上述几个叠加就会 OOM。OOM 前的频繁 GC/交换也会表现为「未响应」。

### 9.4 死路径与重复

- 移动端从不启用 GPU cull：`upload_all_notes_for_cull` / `upload_summary_for_cull` 只有桌面和测试调用，`CullState::is_ready()` 恒 false，`draw` 永远走 `draw_legacy`（`renderer.rs:610-628`）。如果移动端没有启用计划，`InstanceRenderer` 里的 cull 状态、per-key buffer、dispatch 参数对 Flutter 是纯负担。
- `effective_visible` 有两份：`render.rs:603-610` 和 `mobile-core/src/viewport.rs:26-34`。
- `crates/yinhe-wgpu/src/render_thread.rs` 是桌面 fallback，和 `crates/yinhe-flutter/src/lib.rs` 的渲染线程职责重复。
- `build_notes` 的每 key `vec![Vec::new(); num_tracks]` 与 `flush_track_bucket` 的过滤顺序可以合并。
- `Selection` 顶部注释「1 亿全选 = 1 个 rect」已与 `select_all_pr` 的按轨 rect 实现不一致。

## 10. 量级估算总表

> 估算前提：1 亿音符、300 万 tick、手机 4-8 核、顺序扫描 2-5ns/音符、BTreeMap 命中 50-100ns/次、Dart 对象分配 30-80ns/个。仅用于排序。

| 场景 | 1 万 | 100 万 | 1 亿 |

| AR 播放跟随/滚动单帧 | <1ms | 0.3-3ms（默认）/ 8-30ms（全曲） | 100ms-1s（默认）/ 1-5s（全曲） |
| PR 跨窗口重建 | <1ms | 0.3-2ms | 8-40ms（默认）/ 1-10s（全曲） |
| 力度摘要一次 | <1ms | 10-35ms | 0.8-3s（8×全曲） |
| move 快路径松手 | <1ms | 20-60ms | 2-6s |
| move 慢路径松手 | 1-3ms | 0.3-1s | 30-120s |
| scale 松手 | 2-5ms | 0.2-0.5s | 30-90s |
| erase 松手 | 2-5ms | 0.2-0.5s | 20-40s |
| Riff（K=8） | ~10ms | 1-3s | 60s+ / OOM |
| 选区 ghost 物化 | <1ms / 120KB | 30-100ms / 12MB | 3-10s / 1.2GB（全选 T×N 更慢） |
| AM 锚点拖动每帧 | <1ms | 5-15ms | 0.5-1.5s |

## 15. 需要决策 / 暂未修复

以下改动收益明确，但涉及产品行为或跨模块设计，先留给你决定：

1. **AR 首次打开仍会扫描当前视口内的全部音符**。CPU Cull 不再建窗口，但 1 亿音符工程在默认整曲缩放下首帧仍要处理约 15%-30% 全曲。是否把移动端 AR 初始缩放改成「只适配前 N 小节 / 当前视口附近」，需要你定产品行为。
2. **`yinhe_render_frame` 已改为非阻塞**。500ms 已删除；慢帧现在只让纹理更新变慢，不再冻结 UI。若发现选框/播放头与纹理差一帧，再加 overlay frame revision，而不是恢复同步等待。
3. **空闲 ticker 仍常驻 60/120fps**。按需启动需要一套 `_needsFrame` 状态机（播放、惯性、拖拽、长按圆环、主题过渡、AM 动画、surface 重建），漏一个就会让动画停住。建议单独一轮改并逐项回归。
4. **`automation_json` 仍一次返回该轨所有 lane**。拆成「lane 元数据 + 当前 lane 点」会让切 lane 多一次异步加载；AM 面板需要接受短暂 loading/空点状态。
5. **事件列表分页仍是 `skip` 语义**。改成 `(tick, 稳定 id)` 游标要改 FFI 签名和 Dart 分页协议，收益只在「打开事件列表并跳到同 tick 巨簇」时体现。
6. **轨道重排/删除仍全量重写音符**。要根治需要「稳定 track id」或全局 remap 表，渲染、音频、选区、undo 都要一起改；单独改一处会引入语义分叉。
7. **大选区 move/scale/Riff 仍在 UI 线程**。统一走 `doc_job` 会改变「松手立即看到结果」的交互，需要决定是否接受 1-2 帧延迟或进度框。
8. **音频初始化仍在 AUDIO 锁内同步 spawn**。移到后台启动需要处理「首次播放时引擎还没就绪」的状态；桌面对应实现可参考，但移动端要定首播延迟策略。

已按第 16 节落地、不再需要决策：拖动 ghost 的 `by_key` 全量缓存、`select_all` 立即物化（见第 16 节第 3、4 项）。

## 16. 2026-11-21 决策：取消窗口缓存/兜底，移动端走 CPU Cull

以下是对第 15 节部分项的最终取向，按“根因优先、不要缓存、不要阈值、不要兜底”执行：

1. **AR 不再建 2 个跨度的窗口缓存**。撤销 `note_window` 的窗口实例缓存，改为移动端 CPU Cull：
   - 按 key 的 chunk（`NoteBucket` 的 65536 音符块）维护 `max_end_tick`；
   - 每帧只遍历与视口相交的 chunk，流式合并后直接产出实例；
   - 不保留窗口副本，不增加持久显存；
   - 低倍率下如果仍慢，再评估“按 tick 块的 LOD 摘要”作为派生索引，而不是窗口缓存。
2. **删除 `max_note_len_by_key` 和脏 key 写 `u32::MAX` 的兜底**。用 `NoteBucket` 的 chunk `max_end_tick` 作为精确左界：块内最大 end < 视口起点就整块跳过；不再需要全局/每 key 的最长音符回看，也不需要“未知就全范围扫”。
3. **拖动 ghost 不再按 12B/选中音符存 `by_key`**。改为：
   - 选区只保留成员位图（1 bit/音符）；
   - 拖动时每帧只扫描当前视口内的 chunk/音符，查位图决定是否生成 ghost；
   - 删除 `DRAG_IN_FLIGHT` single-flight、`GARBAGE_TX` 后台析构线程和 `drop_drag`。
4. **`select_all` 不再立即后台物化成员位图**。全选保持矩形态；第一次拖动/需要成员时再物化。`move_selected_notes` 快路径本来就会在移动时用 `NoteBitsetBuilder` 收集实际成员，不需要预热。
5. **marker 排序不再做 Dart 侧缓存**。Rust 的 conductor 事件本来就按 tick 有序，Flutter 直接使用原列表，不排序、不缓存。
6. **`yinhe_render_frame` 的 500ms 已删除**。按“不要兜底”的原则改成了非阻塞请求；若后续需要纹理与浮层严格同帧，用 frame revision，不要恢复固定毫秒超时。
7. **原则**：如果某个优化必须依赖“窗口/缓存/脏标记回退”，优先改成数据结构本身的可查询索引（如 chunk max_end）；索引必须跟随写路径维护，而不是旁路缓存。
