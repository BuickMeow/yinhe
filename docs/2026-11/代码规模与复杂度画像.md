# 银河（yinhe）代码规模与复杂度画像

> 日期：2026-11-18
> 目的：评估哪些功能比预想复杂、哪些可以简化或砍掉，以保证工程长期可维护。
> 口径：`git` 跟踪的文本文件；物理行；Rust「代码行」= 非空且不以 `//` 开头；
> 「测试」= `#[cfg(test)]` 修饰的 `mod`/`fn` 块 + `tests.rs`/`*_tests.rs`/`tests/`/`engine_tests/`
> + `#[cfg(test)]` 的 bench 文件。数字为近似值，用于量级比较，不作 KPI。

## 6. 比预想复杂的部分

按「实际行数 / 直觉预期」排序：

1. **本地化数据**：YAML 21,116 + Dart l10n 11,503 = **32,619 行**，比整个音频引擎（~9k）和合成器（~4.6k）加起来还多。它不是逻辑，但每次改文案、加语言都在增加维护面。
2. **Flutter 移动端**：Rust 14,299 + Dart 20,634（不含 l10n）= **约 3.5 万行**，几乎是一个独立客户端；测试代码只有 180 行。
3. **UI 基础设施**：App 壳 11,495 + 通用控件 7,162 + 窗口外壳 7,069 + 对话框 8,321 = **约 3.4 万行**，和所有音频相关代码相当。
4. **事件浏览器**：4,300 行，比 MIX 混音台（4,797）只少一点；它支持每种事件类型一个编辑器。
5. **设置对话框**：3,400 行，其中快捷键可视化 + 主题编辑器 + 键盘布局约 2,300 行。
6. **插件宿主**：CLAP + VST3 + 扫描 + UI 约 7,100 行，接近整个音频引擎核心。
7. **自动化**：跨 PR/AR/通道 AR/类型/GPU/编辑器约 7,000 行，是隐性大头。
8. **主题预设**：`theme/base/presets.rs` 1,077 行，只是颜色数据，却比 `yinhe-mixer` 整个 crate 的生产代码（1,901）的一半还多。
9. **MIDI writer** 928 行 > parser 721 行：写回比解析更复杂（弯音、RPN、多轨、格式化）。
10. **`document/automation_edit.rs`** 975 行：一个「编辑命令落地」文件接近 1 千行，因为要覆盖轨道/Conductor/混音节点三类 × 增删改/批量/形状。

## 7. 可简化 / 阉割候选

> 以下为**基于代码规模的建议**，不代表必须做。每项都标了大致可节省行数与风险。

### A 档：边界清晰、节省巨大

| 候选 | 可节省（近似） | 影响 | 风险 |
|---|---:|---|---|
| **移动端 Flutter 整套**（Rust 桥 + Dart UI） | ~35,000 行（14.3k Rust + 20.6k Dart，不含 l10n） | 失去 Android/iOS/OHOS | 高（产品决策） |
| **多语言**：保留 zh-CN + en-US，其余 13 种移除 | ~25,000 行（YAML ~18k + Dart l10n ~7k） | 只影响非中英文用户 | 低 |
| **第三方插件宿主**（CLAP + VST3 + 扫描 + 机架 UI） | ~7,000 行 | 只能用内置音源/内置 insert | 中（专业用户） |
| **事件浏览器编辑能力**（保留只读列表） | ~2,500~4,000 行 | 不能逐事件编辑，仍可看 | 中 |
| **设置高级项**（快捷键可视化/键盘布局/主题编辑器） | ~2,300 行 | 设置变简单 | 低 |

### B 档：局部功能，节省中等

| 候选 | 可节省 | 说明 |
|---|---:|---|
| 归档密码/加密 + 7z 解包 + 归档选择器 | ~1,000 行 | `archive` + `midi_7z` + `archive_picker` |
| Domino 剪贴板 + 文件剪贴板 + 选择剪贴板 | ~950 行 | `domino_clipboard` + `clipboard_file` + `clipboard` |
| 主题预设精简（只留 2~3 套） | ~800 行 | `theme/base/presets.rs` |
| 动态跟随 / 轨道活跃度 / 和弦检测 | ~700 行 | 三个独立小功能 |
| 音频片段高级操作（warp/淡入淡出/归一化/反向） | ~800 行 | `audio_source` + `audio_clip_edit` + `audio_warp` |
| 电平表可视化（频谱/声谱/示波/波形，保留 VU） | ~450 行 | `yinhe-meter` 的视觉部分 |

## 8. 如果目标是「更简洁」，推荐优先级

1. **先做零风险的「数据瘦身」**：语言文件从 15 种减到 2 种；主题预设从多套减到 2~3 套。可减约 2.6 万行，几乎不动逻辑。
2. **再决定移动端去留**：这是最大的一块（约 3.5 万行）且测试覆盖率最低（1.2%）。如果不做移动端，冻结/移出 workspace 比继续维护更划算。
3. **插件策略二选一**：只保留 CLAP 或只保留 VST3，可省约 1.3k 行宿主 + 一部分 UI；若只做内置音源，可省约 7k 行。
4. **事件浏览器降级为只读**：保留查看与定位，砍掉逐事件编辑器，可省 2.5k~4k 行，且不影响主要编辑流程。
5. **最后再考虑重构大文件**：`spawn.rs`、`arrange.rs`、`document.rs` 的拆分不减少功能，只降低单文件复杂度，优先级低于上面的「砍功能」。

## 9. 复现方法

本文件的数字可用以下方式复现（脚本思路）：

1. `git ls-files '*.rs'` 枚举 Rust 文件。
2. 排除 `tests/`、`engine_tests/`、`*tests.rs`、`*_tests.rs`、`bitmap_bench.rs`、`bench.rs`（整文件测试）。
3. 对每个文件扫描 `#[cfg(test)]` 修饰的 `mod`/`fn` 块，按花括号配对求出测试区间；其余为生产代码。
4. 代码行 = 非空且不以 `//` 开头的行；总行 = 物理行。
5. 按 crate 与目录前缀聚合；功能域映射规则见本文件表格分组。

> 建议把该脚本收进 `xtask loc`（未来可做），避免每次手工统计口径漂移。
