## 1. 纹理更新变慢，有没有更快的办法

### 1.1 先分清两个“帧率”

现在 `yinhe_render_frame` 已经是非阻塞请求：

- **Flutter UI 帧率**：60/120Hz，基本不受 GPU/渲染线程影响；
- **画布纹理更新率**：约等于 `1 / 渲染一帧的时间`。

低倍率下 AR 一帧要处理几百万到几千万可见音符，纹理自然只能 5-15fps；但输入、菜单、滚动不会因此冻结。想同时提高纹理更新率，只有一条路：**减少每帧真正要画的音符数**，没有别的魔法。

### 1.2 当前一帧花在哪

移动端 AR（`build_notes_culled`）：

```
可见 tick 范围 → 每个 key 取相交的 NoteBucket chunks
→ 逐音符过滤 track/显隐/hidden
→ 按轨道流式合并（亚像素）
→ 写 NoteInstance
→ queue.write_buffer 上传
→ draw + present
```

低倍率时“逐音符过滤/合并”就是主要成本。PR 在低倍率已经走摘要层，成本主要是一次 `build_key_summary_in_range` 扫描；AR 还没有 LOD。

### 1.3 可选加速手段（按收益/复杂度排序）

| 手段 | 收益 | 代价 | 评价 |
|---|---|---|---|
| **AR/PR 共用 CPU LOD 摘要** | 低倍率数量级提升 | 需要按 revision 构建摘要；粗档内存很小 | 推荐，根因方案 |
| 去掉每帧重复的自动化 lane 构造 | 中低 | 需要廉价 key 或让 shader 算 y | 值得做 |
| 空闲 ticker 停帧 | 中 | 需要完整 wake 状态机 | 值得做，但不影响单帧耗时 |
| CPU cull 已有 rayon 并行 | 已生效 | 128 key 并行已够；再嵌套并行会超订 | 不建议再加并行 |
| GPU cull（持久 per-key buffer） | 高 | 显存大；1 亿音符不现实 | 手机不优先 |
| 动态分辨率/降采样 | 高 | 画面变糊；产品不接受 | 不做 |
| 降低交互时刷新率 | 省电 | 纹理更慢，不解决问题 | 不做 |

“纹理更新慢”不是靠调大/调小某个毫秒数解决的；如果低倍率必须显示整曲，就必须用 **LOD 摘要** 把“每帧遍历全部可见音符”降成“每帧遍历可见摘要块”。

## 2. Ticker 是什么，空闲怎么停

### 2.1 Ticker 不是定时器

Flutter 的 `Ticker` 是 **vsync 驱动的帧回调**：

- `Ticker.start()` 会向 `SchedulerBinding` 注册一个每帧回调；
- 只要 ticker 还 active，它自己在每次回调后继续请求下一帧；
- 所以当前代码末尾的 `SchedulerBinding.instance.scheduleFrame()` 其实是冗余的。

当前 `studio_shell.dart` 的自定义 ticker 同时做了三件事：

1. 请求 Rust 渲染（`renderFrame`）；
2. 同步视图/浮层/时间码；
3. 每 4 帧、每 60 帧轮询后台状态（文档任务、音色库、自动保存、音频恢复）。

它不能靠“跳过 `renderFrame`”来省电，因为 active ticker 仍会持续产生 Flutter 帧。要空闲停帧，必须 `stop()`。

### 2.2 正确修法

1. **定义 `_needsFrames`**：
   - 播放中；
   - 手指按下/拖拽/缩放；
   - `rust.dragTick()` 仍返回 1（惯性/边缘滚动）；
   - 长按圆环、选框锚点出现、音符删除淡出、marquee hint；
   - 主题过渡、AM 纹理预热；
   - 文档任务/压缩包/音色库/保存仍在跑。
2. **不满足时 `_ticker.stop()`**，不是 `return`。
3. **`_wake()` 里 `_ticker.start()`**：
   - 根节点套一个 `Listener`，任意 pointer down/move/up 都 wake；
   - `AppLifecycleState.resumed`、程序性加载完成、菜单动作也 wake。
4. **把后台轮询移出渲染循环**：
   - `docState`、`archiveStatus`、`sfLoadingJson`、`documentGeneration`、`autosaveTick`、`recoverAudio` 改用 `Timer.periodic` 或任务启动时唤醒；
   - 否则 ticker 停了，后台任务完成也没人轮询。

### 2.3 为什么没有立刻改

风险不在性能，而在“漏一个 wake 导致动画停住”。需要逐项回归：播放、拖动、惯性、长按、选框锚点、删除淡出、主题切换、AM 展开、加载/保存进度。这是一轮独立的 UI 状态机改动。

## 3. CPU LOD 摘要：与现在 CPU Cull、2 跨度窗口、桌面端的关系

一句话：**窗口缓存是“把同一份全分辨率实例按视口切一块存起来”；LOD 摘要是“模型本身的一层更粗表示”**，类似 mipmap。

| 维度 | 2 跨度窗口缓存 | CPU LOD 摘要 |
|---|---|---|
| 缓存内容 | 2 个屏幕范围的全分辨率 `NoteInstance` | 按 key/track/tick 块聚合后的少量摘要实例 |
| 生命周期 | 跨窗口就失效；滚动/缩放/编辑会重建 | 按模型 revision 构建；滚动不失效，只在缩放跨档/编辑时重建 |
| 显存/内存 | 接近 2 屏原始实例；低倍率仍然很大 | 粗档很小；只上传当前选中档 |
| 每帧工作 | 窗口内直接上传，几乎不重建 | 每帧只遍历可见摘要块（数量远小于原始音符） |
| 编辑成本 | 每次编辑都让当前窗口失效 | 只让受影响 key/块失效；第一版可以整层重建 |
| 视觉 | 精确 | 低倍率下块内细节不可见，视觉等价；高倍率用原始层 |
| 复杂度 | 缓存键、失效、窗口边界、预取 | LOD 档位选择 + 摘要构建 + 失效 |
| 本质 | 视口缓存 | 数据表示降级 |

移动端已经删掉 2 跨度窗口。下一步如果做 LOD，**不是把窗口换个名字**：不会按 `scroll_x/scroll_y` 存实例，摘要和视口无关，只和模型 revision/缩放档有关。

### 3.1 和“现在这版 CPU Cull”的关系

现在这版是**纯原始层 CPU Cull**：

```
可见 tick 范围
→ 每个 key 取相交的 NoteBucket chunks
→ 逐音符过滤/合并
→ 写 NoteInstance
```

复杂度是 O(可见区原始音符数)。低倍率慢就是因为这个 O(N_visible)。

新 LOD 不是替换它，而是**同一个 cull 路径里的两条分支**：

```
按 ppu 选一个 tick 块宽 block（沿用 SUMMARY_BLOCK_TICKS 的连续公式）
按 (key, track, block) 取摘要
每个可见块：
  投影宽度 = block * ppu
  if 宽度 <= 4px: 直接输出该块的摘要实例
  else: 回退到该块范围内的原始音符，逐音符合并
```

- 高倍率：块很宽 → 基本都走原始层，和现在一样；
- 低倍率：块很窄 → 走摘要，不再遍历块内全部音符；
- 中倍率：同一帧里混合，窄块摘要、宽块原始；
- 没有全局“模式开关”，没有窗口缓存；摘要按模型 revision 维护，滚动不失效。

建议的摘要粒度是 **(key, track, tick_block)**，因为 AR 需要按轨道分行；PR 可以继续用它已有的 key/tick-block 摘要（主导轨）。

内存量级：

- block=4096、300 万 tick 时，每 key 约 732 个块 × 128 key ≈ 9.4 万块；
- 每个块按有音符的轨道存一条摘要（12–16B），20 条可见轨约 20–30MB；
- 100 条轨约 100–150MB；
- 默认整曲 AR 的 ppu 约 0.00085，block≈4096（约 3.5px），这是最常用的粗档；再缩小会用更粗的 block，内存更小。
- 只保留“当前 ppu 选中的档”，不要一次构建 8 档；编辑时按 `note_revisions` 只重建脏 key。

构建成本：一次全曲扫描（100M 约 1–3s，后台），显示进度；编辑一个 key 只重建该 key 的摘要（约 78 万音符，几十 ms）。

**当前实现（`0a6fc2cf`）**：

- `yinhe-types` 定义 `NoteSummary` / `KeySummary`；`yinhe-core::lod` 负责 `(key, track, block)` 聚合与单档缓存；
- `NoteSource::key_summary(key, block_ticks)` 默认返回 `None`，`YinModel` 用 `note_revisions` 判定缓存是否有效；
- `build_notes_culled` 在 `SUMMARY_MAX_PX` 内走摘要，否则回退原始层；
- 隐藏集合非空（拖拽 ghost）时回退原始层——聚合段无法准确减掉单个被隐藏音符；
- 摘要只保留当前块宽一档，跨档会重建；构建发生在渲染线程首次需要该档时，尚未后台化/显示进度。

### 3.2 和桌面端的关系

- `NoteBucket` / `NoteSource` / `SUMMARY_BLOCK_TICKS` 是共享类型；如果摘要构建放在 `yinhe-core` 或 `yinhe-types`，**桌面 AR 可以直接复用**。
- 桌面 PR 现在已经有 GPU cull + `SUMMARY_BLOCK_TICKS` 摘要层（`cull/summary.rs`），那是 GPU 侧的另一种 LOD；桌面 AR 已切到 `build_arr_notes_culled`，和移动端共用 CPU 摘要，缓存键也去掉了 scroll_y。
- 所以：
  - 移动端 AR：需要 CPU LOD（显存不够走 GPU 持久 buffer）；
  - 桌面 AR：可以复用同一份 CPU 摘要，或继续走自己的 GPU 路径；
  - 桌面 PR：已有 GPU 摘要，不需要重复做 CPU 摘要。
- 结论：**摘要的数据结构放共享层，渲染分支各壳自己接**；不要只写在 `yinhe-mobile-core`，否则桌面 AR 还得再实现一遍。

## 4. `yinhe-core` 和 `yinhe-mobile-core` 是并行的吗

不是。当前是纵向分层，不是两个平行核心：

```
yinhe-types         数据原语（Note/Bucket/View/Automation/TimeFormat）
   ↑
yinhe-core          YinModel、TempoMap、Selection、NoteBucket 写路径、统计/索引
   ↑
yinhe-editor-core   Document、历史/命令、选区语义、剪贴板、导入合并、Track 操作
   ↑
yinhe-mobile-core   移动端会话：scene 投影、触屏手势、音频会话、doc_job/autosave/import/export
   ↑
yinhe-flutter       FFI/JNI/纹理/surface/平台胶水
```

桌面端 `yinhe-egui` 直接使用 `types/core/editor-core/wgpu/audio`，不经过 `mobile-core`。所以：

- `yinhe-mobile-core` 是 `yinhe-core` 的**上层应用核心**，不是并行替代；
- `yinhe-flutter` 是平台壳，负责 FFI 和 surface；
- `yinhe-core` 偏“数据模型和存储”，`editor-core` 偏“文档命令和历史”，`mobile-core` 偏“移动端会话和 UI 投影”。

## 5. 哪些可以下放到 `yinhe-core`

先说边界：**不要把所有东西都塞进 `yinhe-core`**。它现在小，是因为它只做数据模型；把 JSON、线程、FFI、UI 投影塞进去会变成上帝 crate。

更合理的层次是：

- `yinhe-types`：纯数据/几何/格式化原语；
- `yinhe-core`：模型、索引、选择语义、NoteBucket；
- `yinhe-editor-core`：Document 命令、历史、导入合并；
- **新增 `yinhe-app-core`（建议名）**：与 UI 无关的会话/任务层：doc_job、autosave、recent/library、导入导出状态机；
- `yinhe-mobile-core` / `yinhe-egui`：各自壳的会话、手势、投影、平台适配。

可下放/可抽出的候选：

| 当前模块 | 性质 | 建议去向 | 说明 |
|---|---|---|---|
| `mobile-core/inertia.rs` | 纯视口物理 | `yinhe-types` 或 view-core | 与 UI 无关，桌面也可复用 |
| `mobile-core/viewport.rs::effective_visible` | 纯过滤函数 | `yinhe-types` | 现在 `yinhe-flutter/render.rs` 还有一份拷贝，先合并 |
| `mobile-core/scene/view.rs` 的标尺/网格/时间码数学 | 纯计算 | `yinhe-types/time_format` 或 view-core | JSON 输出留在 mobile-core |
| `mobile-core/doc_job.rs` | 通用后台文档任务 | `yinhe-app-core` | 不依赖 Flutter，桌面也能复用 |
| `mobile-core/autosave.rs` | 通用自动保存 | `yinhe-app-core` | 目前只被移动端用，但逻辑与平台无关 |
| `mobile-core/library.rs` | 最近工程索引 | `yinhe-app-core` | 文件路径/工程头读取，与 UI 无关 |
| `mobile-core/midi_import.rs` 状态机 | 后台解析 + 摘要 | `yinhe-app-core` | 合并逻辑已在 editor-core |
| `mobile-core/midi_export.rs` | 后台导出状态机 | `yinhe-app-core` | 写入逻辑在 yinhe-midi |
| `mobile-core/selection_materializer.rs` | 异步成员位图 | `yinhe-app-core` 或 editor-core | 需要可注入的调度器 |
| `mobile-core/audio.rs` | 移动音频会话 | 部分下沉 `yinhe-audio` | 设备/线程管理可复用，平台生命周期留在壳 |
| `mobile-core/edit/` 手势状态机 | 触屏手势 | 暂留 | 与桌面鼠标交互差异大，强行共享会分叉 |
| `mobile-core/scene/` JSON 投影 | Flutter 协议 | 留在 mobile-core | 不要进 core |
| `mobile-core/theme_colors.rs` / `velocity_cache.rs` | UI/渲染缓存 | 留在 mobile-core | 平台/渲染特定 |
| `mobile-core/midi_names.rs` | 名称表 | `yinhe-midi` 或 types | 纯数据 |

判断标准：

- 只依赖 `types/core`、不依赖 UI/线程/JSON → 可以下放；
- 依赖 Flutter、Dart、JNI、纹理、平台生命周期 → 留在壳；
- 只是“移动端目前唯一使用”，不代表必须留在 mobile-core。

## 6. “面多了加水、水多了加面”的逻辑

以下是当前代码里比较像“为了绕过一个设计问题又加一层”的地方，按确定性排序。

### 6.1 已确认的遗留/冗余

1. **全局 `max_note_len` 在块级索引之后已经没用了**
   - `model.rs:903`、`model_stats.rs:251` 仍在维护；
   - `source.rs:37` 的 `YinModel::key_notes_in_range` 已经改用 `NoteBucket::range_including_long`，不再读它；
   - 只剩 `NoteSource::max_note_len` 的默认实现可能用到，但 YinModel 自己不走默认实现。
   - 根因处理：删除全局字段和统计更新，或明确只给非 YinModel 的 NoteSource 用。

2. **marker 删除/粘贴却调用 `reload_notes`**
   - `scene/events.rs:692`（删除 marker）、`:899`（粘贴 marker）会 `audio::reload_notes`；
   - marker 不参与音频，`reload_notes` 却会重建 CC/audible notes；
   - 同一文件的 marker 插入/重命名/移动只 `refresh_snapshot`，行为不一致。
   - 根因处理：marker 操作只刷新场景，不重载音频。

3. **`SnapCtx` 每次构造都 clone 整份拍号事件**
   - `scene.rs:64`：`events: m.tempo_map.time_sig_events.clone()`；
   - `SnapCtx::new` 在每次 pointer update / 拖拽里调用；
   - 黑乐谱拍号事件多时，每个手势帧都在复制 Vec。
   - 根因处理：改成借用 `&[TimeSigEvent]`，或存 `Arc`。

4. **`effective_visible` 有两份**
   - `yinhe-flutter/src/render.rs:598` 与 `mobile-core/src/viewport.rs:26` 算法相同；
   - 两份都每帧分配 `Vec<bool>`。
   - 根因处理：合并到 mobile-core/types，返回 `Cow<[bool]>`，无 `display_track` 时不分配。

5. **标尺/网格/时间码各自重算拍号分段**
   - `scene/view.rs::ruler_labels_json` 与 `time_grid_json` 各 `build_time_sig_segments` 一次；
   - `format_tick_bar_beat_with_time_sig` 每次调用也重建；
   - 同一帧内同一份拍号事件被解析多次。
   - 根因处理：TempoMap 构建时保存分段/累计 bar offset，或一帧内只算一次传给三个消费者。

6. **`view_snapshot` 混了视口、音频时间和待应用选区**
   - `scene/view.rs:563`：先 `apply_pending`，再 `playback_tick_for`，再算 BPM/拍号/视口；
   - 一个“快照”同时依赖 scene、audio、selection materializer；
   - 锁顺序和刷新时机都复杂。
   - 根因处理：拆成 view snapshot 与 transport/time 两个无副作用读取，或先取模型/音频快照再拼。

7. **`bucket_max_end_tick` 和 `NoteBucket.max_ends` 重复**
   - `YinModel.bucket_max_end_tick` 是每 key 的最大 end；
   - `NoteBucket.max_ends` 是每 chunk 的最大 end；
   - `tick_length`/统计又依赖前者。
   - 根因处理：`tick_length` 从 `NoteBucket.max_ends.iter().max()` 派生，删掉每 key 的重复字段。

8. **`NoteBitset::insert` 和 `NoteBitsetBuilder::insert` 两套实现**
   - `note_bitset.rs:134` 的逐位 insert 与 `:76` 的 builder 做同一件事；
   - 热路径已经部分改用 builder，但仍有路径用慢的。

## 7. Android “未响应”能不能按需不弹

结论：**不能由 App 决定“这次不弹”**。

### 7.1 ANR 是谁弹的

ANR 是 Android 系统的 `ActivityManagerService`/`InputDispatcher`  watchdog 弹出的：

- 输入事件 5s 内没处理完；
- BroadcastReceiver 前台 10s / 后台 60s；
- Service 前台 20s / 后台 200s；
- ContentProvider 10s。

App 没有 API 可以拦截、延迟或“申请不显示”系统 ANR 对话框。开发者选项里的“显示所有 ANR”只是用户/开发者设置，不是 App 权限。OEM 可能自定义，但不能依赖。

### 7.2 “程序认为问题不大”应该怎么表达

不是让系统别弹，而是让主线程真的保持可响应：

- **重活全部放到后台线程**（Rust worker / Dart isolate / doc_job），UI 线程只更新进度；
- **UI 线程不跨 FFI 同步等长任务**（这次 renderFrame 已改成非阻塞）；
- 大 JSON 解码、全量自动化/事件序列化、1 亿选区提交，不应在 UI isolate 上做；
- 长任务显示确定/不确定进度、允许取消，让用户看到“还活着”；
- 需要 UI 线程分段处理时，用 `await Future.delayed(Duration.zero)` / 分帧让出，避免连续 5s 不处理输入。

如果主线程保持响应，后台跑几个小时也不会 ANR；如果真死锁/主线程卡死，ANR 是正确行为。抑制它只会掩盖数据丢失/死锁问题。

### 7.3 黑乐谱的特殊性

黑乐谱单个操作比普通 MIDI 慢很多是正常的。正确 UX 是“进度 + 可取消”，不是“假装没卡”。把长操作做成后台任务后，系统不会因为耗时长而 ANR；只有主线程被阻塞才会。

## 8. 统一进度条 / 任务中心

现在进度相关的东西是分散的：

- `_sfProgress`：底部音色库加载进度条（`studio_shell.dart:300`、`_readSfProgress`）；
- `showTaskProgressDialog`：文档任务/导出的模态进度框（`flutter/lib/dialogs/progress_dialog.dart`）；
- `_runDocJob`：等待 150ms 再决定是否弹框；
- 压缩包导入、导出、保存各自一套状态。

用户要求“所有潜在高耗时场景都加进度条”，而且可以复用音色库/音频引擎加载的进度条。建议收敛成一个 **TaskCenter**：

### 8.1 Rust 侧

一个通用任务表：

```rust
struct Task {
    id: TaskId,
    title: String,
    detail: String,
    state: Queued | Running | Done | Failed | Canceled,
    stage: String,
    done: u64,
    total: Option<u64>,   // None = 不确定进度
    unit: WorkUnit,       // Notes / Bytes / Frames / Chunks
    cancel: Arc<AtomicBool>,
}
```

注意这里**不存 `f32` 百分比**，只存 `done/total` 整数和单位。百分比由 UI 现算，任务内部只负责如实累加工作单位；这样类型层面就不允许“拍一个 50% 出来”。

- 现有 `doc_job` 变成任务类型之一；
- MIDI 导入/导出、保存、音色库加载、压缩包导入、LOD 摘要构建、大选区提交、轨道重排/删除都注册任务；
- FFI 只暴露两个入口：`tasks_json()`（活动任务列表/摘要）和 `task_snapshot(id)`（详情/进度）；
- 不再为每个功能加一套 `*_status_json` / 全局 slot。

### 8.2 Dart 侧

- `TaskCenter` 用 `ValueNotifier<List<TaskInfo>>`，4–8Hz 轮询一次（不要每帧 JSON）；
- 后台任务：底部细进度条，复用现有 `_sfProgress` 的视觉；
- 阻塞任务（打开/保存/导出/导入）：模态进度框，复用 `showTaskProgressDialog`，带取消；
- 多任务：底部显示最靠前的一个，点开展开列表；不要把多个进度条叠在画面上；
- `Option<f32>` 为 None 时用不确定动画，不伪造百分比。

**当前实现（`c5f044ef`）**：先做了“单一视图”，没有一次性替换所有状态槽。

- Rust 新增 `task_center::tasks_json()`，把 doc_job、MIDI 导入/导出、音频导出、压缩包、音色库加载聚合成 `{"tasks":[...]}`；
- FFI 只加 `yinhe_tasks_json`，Dart 每 200ms 轮询一次；
- 底部只显示第一条运行中的任务，复用原音色库进度条的视觉；
- 现有 `*_status_json` 仍供旧对话框使用，后台线程没有重写。

因此“类型层面强制 done/total”目前只在新代码里推荐，旧任务仍是 `f32`。下一步是把 doc_job / 导入 / 导出 / 保存逐个改成 `Progress` 句柄，然后删掉旧槽。

### 8.3 哪些操作应该接进来

| 操作 | 现状 | 建议 |
|---|---|---|
| 打开工程/MIDI | 已有进度框 | 注册为任务 |
| 保存工程/MIDI/音频导出 | 已有进度框 | 注册为任务 |
| 音色库加载/压缩包导入 | 已有底部/进度 | 注册为任务 |
| LOD 摘要构建 | 无 | 后台任务，raw 层先显示 |
| 大选区 move/scale/Riff/erase | UI 线程 | 后台任务 + 进度 + 取消 |
| 轨道重排/删除 | UI 线程全量重写 | 后台任务 + 进度 |
| 事件列表远页 | UI 同步分页 | 后台任务/分页加载 |
| 音乐库/SFZ 诊断 | UI 同步扫盘 | 后台任务 |
| 自动化全量 JSON | UI 同步 | 优先改成视口/lane 范围，不必加进度 |

### 8.4 原则

- 进度条不是“遮住卡顿”，任务本身必须在后台线程；
- 主线程只做 UI 和进度更新；
- 任务可取消的必须真的能取消（worker 定期检查 cancel）；
- 不伪造百分比；不知道总步数就用不确定进度；
- 任务失败要保留错误信息，不要只关框。

## 9. 进度回调怎么保证有数据量意义

先给结论：**进度 = 已完成工作单位 / 总工作单位**。想避免 `0% → 100%` 和 `0% → 7% → 100%`，不是靠 UI 平滑动画，而是靠三件事：

1. 单位必须是真实工作量（音符、字节、帧、块），不能是容器个数（轨道数、key 数、文件数、stream 数）；
2. 总量必须在开始前已知，或能在 O(1) 内从已有统计拿到；拿不到就显示**不确定进度**，不伪造百分比；
3. 回调必须发生在工作循环内部，按固定工作块累加；不能只在阶段边界报一次。

一个简单的自检：**把音符总数扩大 10 倍、其它条件不变，进度曲线应该还是均匀的**。如果“1 条轨 5000 万音符”和“16 条轨 5000 万音符”的曲线完全不同，说明单位选错了。

### 9.1 实现形态

```rust
pub struct Progress {
    stage: usize,
    done: u64,
    total: u64,
    last_emit: Instant,
}

impl Progress {
    /// 每处理一个自然工作单位就调用；累加是 O(1)，发射由时间节流。
    pub fn advance(&mut self, units: u64) {
        self.done += units;
        if self.last_emit.elapsed() >= Duration::from_millis(100) || self.done >= self.total {
            self.emit();
            self.last_emit = Instant::now();
        }
    }
}
```

阶段权重也必须来自数据量，而不是手写常数：

```rust
struct Stage { name: &'static str, weight: u64 } // weight = 该阶段预计工作单位数
// 总进度 = Σ(已完成阶段 weight) + 当前阶段 weight × done/total
```

- 阶段权重优先用已有统计：`model.note_count`、`track_note_count`、文件字节数、压缩包条目 `size`、采样字节数；
- `YinModel` 已经维护 `note_count`，所以“按音符加权”通常是 O(1)，不需要额外扫描；
- 只有在总量真的未知时（例如第一遍扫描事件流），才用**不确定进度**，不要拿“已扫轨道数”冒充总量；
- 进度只表示**工作量**，不表示剩余时间。黑乐谱各 key/各轨分布极不均匀，ETA 一定会骗人，不做。

几条硬规则：

- **单调**：`emit(max(last, next))`；同一任务跨阶段不能回退。如果解析和合并是两个任务，要么合成一个多阶段任务，要么第二个任务从明确的阶段名重新开始，不能出现 95% → 0%。
- **静默上限**：任意两次回调之间，真实工作时间不超过几百毫秒。做不到就说明工作单位太大（整条轨、整个文件、整段 zstd），要拆小。
- **取消检查放在同一个采样点**：`advance()` 里顺带读一次 `cancel`，避免为了取消再遍历一遍。
- **不确定态显式化**：JSON 用 `"progress": null`，UI 画不确定动画；不要用 `-1`、`0.5` 或“先给 5% 撑住”。

### 9.3 怎么防止以后又写坏

1. **类型约束**：业务代码只能拿到 `Progress`，不能直接持有 `f32` 百分比。没有 `set_progress(0.5)` 这种 API。
2. **强制填单位**：`Progress::new(total, WorkUnit::Notes)`，`total` 为 `None` 时必须显示不确定态。评审第一个问题固定是：“单位是什么？总量哪来的？”
3. **阶段权重可检查**：`Stage` 的 weight 加总必须等于任务总量；debug 断言 `Σweight == total`，阶段切换时断言 `done` 不回退。
4. **测试断言曲线形状**，不只断言首尾：
   - 进度序列单调；
   - 首尾为 0 和 1；
   - 对 100 万音符的假任务，中间不同进度值的数量与工作量同阶（不是只有 1~2 个跳变）；
   - 每个子阶段的 `done` 增量不超过该阶段总量；
   - 这些断言用内存里的 recorder，不依赖真实时间和真实文件。
5. **不在生产代码里加“进度阈值”**：100ms 只是 UI 发射节流，不改变工作量语义；真正决定曲线的是工作单位，不是这个毫秒数。

### 9.4 和 TaskCenter 的关系

- `Task.progress` 只存 `done/total/unit`，UI 现算百分比；
- 后台任务（音色库、LOD 构建、autosave）用底部细条；阻塞任务（打开/保存/导入/导出/rescale）用模态框；
- 一个任务可以有多个阶段，阶段名直接显示“压缩 3/6 列”这种**带数据量**的文案，而不是“处理中…”；
- 任务结束后保留最终 `done/total` 和耗时，失败时保留错误阶段，方便定位。

## 11. 一句话总结

- 纹理更新慢是低倍率真实工作量，不是同步等待；要快只能做 LOD，不能靠调参。
- Ticker 是 vsync 回调，空闲停帧必须 stop/start，不能只跳过 render。
- CPU LOD 是“模型的粗表示”，不是“视口的实例缓存”；后者已经被删除。
- 所有长任务应统一进 TaskCenter：后台执行 + 进度 + 取消；进度条不是用来遮卡顿的。
- 进度必须按真实工作单位计数（音符/字节/帧），总量未知就不确定态，不能按轨道数/key 数/固定分段伪造。
- `mobile-core` 不是和 `core` 平行，而是叠在 `editor-core` 上的移动端会话层。
- `core` 不需要“装更多”，需要的是把平台无关的任务层抽成 `app-core`。
- 代码里确实还有一些“水多加面”：全局 max_note_len、marker 误 reload、SnapCtx clone、重复 effective_visible、拍号分段重复计算、AM 往返、力度条双表示等。
- Android ANR 不能由 App 按需关闭；正确做法是让主线程始终可响应，长任务后台 + 进度 + 取消。
