# 工程格式版本历史

本文记录 `.yin` 工程容器和混音段的版本演进：每个版本对应的 git 提交、日期、
改动原因，以及方案 C 收尾时应该怎么定版本号。

先说结论：

- **`.yin` 容器版本**当前是 **10**，不是 14。
- **混音段版本**当前是 **14**，但混音段 v7..v14 全部是未发布版本。
- 最后发布的混音段版本是 **v6**（`0.1.0-beta.1/2/3`）。
- 方案 C 收尾时，容器保持 **v10**；混音段建议收敛到 **v10**，而不是继续
  保留 v10..v14 五个未发布版本。
- 但要注意：当前代码只支持混音段 v8..v14，**打不开已经发布过的 v6 混音段**。
  如果 beta 包算真实发布，这是一个必须先修的兼容缺口。

---

## 1. 两个版本号不要混

`.yin` 文件里有两个独立的版本概念：

```text
容器版本 VERSION                 // crates/yinhe-yin/src/lib.rs
  └─ header / section framing

混音段版本 MIXER_SECTION_VERSION // crates/yinhe-yin/src/mixer_section.rs
  └─ 第 4 段 MixerParams 的 postcard 结构
```

除此之外还有：

```text
AUDIO_SECTION_VERSION = 1        // 第 5 段音频素材
cover section version = 1        // 封面段
data section                     // 内部有布局演进，但没有单独的 u32 版本号
project.json / mapping.json      // JSON，靠 serde 默认值向前兼容
```

容器版本只负责“文件怎么分帧”，不负责每一段内部字段怎么变。混音段可以单独
升版本，而不需要动容器版本。

所以：

```text
“工程版本 14”这句话不准确。
准确说法是：混音段版本 14，容器版本 10。
```

## 5. 方案 C 的版本策略

### 5.1 容器

建议保持：

```rust
pub const VERSION: u16 = 10;
```

前提是 C 不改变容器分帧和 data 段布局。C 主要改：

- `mapping.json` 里的 TrackData 路由字段；
- 混音段 `MixerParams` 结构。

这些不需要动容器版本。

### 5.2 混音段

按“未发布版本可以合并”的原则，建议：

```rust
const MIXER_SECTION_VERSION: u32 = 10;
```

而不是 14。

理由：

- 最后发布的混音段是 v6；
- v7..v14 全部未发布；
- C 的 schema 变化很大（u16 LC、取消 Bus、AP/LC 统一），继续保留
  v10..v14 五个中间解码器只是在维护开发期快照，没有用户价值；
- v10 正好和容器版本号对齐，讨论时不容易再混。

但需要明确保留哪些旧解码器：

| 目标 | 建议 |
|---|---|
| 已发布 beta.1/2/3 工程 | 必须保留 **v6** 解码器 |
| 这轮 Rack/LC 开发期工程 | 可保留 **v9** 作为最后的开发基线 |
| v10..v14 开发期工程 | 未发布，可删除；如果本地有测试工程，重新保存即可 |
| C 新工程 | 编码 **v10** |

如果 beta 包不算真实发布、可以放弃 v6 工程，则只保留 v9 + v10 即可，代码更少。
但这个决定不能默认做，需要明确。

### 5.3 一个潜在冲突

“混音段最终 v10”会与“未发布的旧 v10（Rack + MixerNode）”撞号。

处理方式：

1. 旧 v10..v14 是未发布开发格式，删除对应解码器；
2. 本地旧工程重新保存；
3. 不要试图同时支持“旧 v10”和“C v10”两种不同结构——postcard 不自描述，
   无法安全区分。

如果希望保留旧 v10 开发工程，就把 C 定为 v15 或 v11；但这就违背“收敛到
v10”的目标。按当前情况，建议接受旧开发工程作废。

## 6. 当前兼容缺口

当前 HEAD：

```text
支持：v8 / v9 / v10 / v11 / v12 / v13 / v14
不支持：v6 / v7
```

已发布 beta.1/2/3 的混音段是 v6。也就是说：

> 如果 beta 包算发布，当前 HEAD 打开 beta 工程时，混音设置会被忽略，
> 但工程本体仍能打开。

这不一定造成崩溃，但会静默丢混音设置，违反“不能静默丢混音设置”的兼容政策。

方案 C 落地前必须二选一：

1. 补 v6 解码器，保证 beta 工程可读；
2. 明确声明 beta 工程不再兼容，并在加载时给出警告，而不是静默忽略。

**当前决定（2026-11-17）：选 2，只保留 v9 + v10。**
如果 beta.1/2/3 之后被认定为正式发布，再单独补 v6 legacy 解码器。

## 7. 复现命令

查看容器版本变化：

```bash
git log --reverse -p -- crates/yinhe-yin/src/lib.rs | rg "VERSION: u16"
```

查看混音段版本变化：

```bash
git log --reverse -p --follow -- crates/yinhe-yin/src/mixer_section.rs \
  | rg "MIXER_SECTION_VERSION"
```

查看发布标签：

```bash
git for-each-ref --sort=creatordate \
  --format='%(refname:short) %(creatordate:short) %(objectname:short)' refs/tags
```

查看某个标签的版本：

```bash
git show 0.1.0-beta.3:crates/yinhe-yin/src/lib.rs | rg 'VERSION'
git show 0.1.0-beta.3:crates/yinhe-yin/src/mixer_section.rs | rg 'MIXER_SECTION_VERSION'
```

## 8. 最终建议

```text
.yin 容器版本：10（已发布，保持）
混音段版本：  10（合并未发布的 v7..v14，保留 v9 + v10 解码器）
beta v6：     不保留；加载时明确警告（除非以后改判为正式发布）
```

这样：

- 对外只有一个清晰的工程版本 v10；
- 不再出现“工程 v14”这种误导说法；
- C 的 schema 只需要一套当前编码器 + 少量旧解码器；
- 省掉 v10..v14 五套迁移快照和测试；
- 兼容政策按当前决定：v9（开发基线）/ v10（C）；beta v6 明确不兼容并警告。
